         the walk clock to zero - and the clock is what stamps

         timeline" is the right rule, and it is right for this

3a. TRANSCRIPT VERIFICATION  (do this first - it is one function)

3b. RECORDING-PART ATTRIBUTION  (second, and only this much)

  The capture chain is NOT touched. Nothing about MediaRecorder,
  chunking, interruption, resume, assembly or export changes.

  What already exists: segment_starts on every session record -
  the chunk index where each recording begins. Chunks are 3s. So
  the app already knows, to within 3 seconds, where each part
  starts in the stitched audio.

  What is missing is one number per part: the walk-clock offset
  at which that part began. Record it at the same moment
  segment_starts is appended - one line, in code that already
  runs there.

  Then export can emit, purely as a translation layer after
  capture:

      parts: [ { part, clock_from_s, clock_to_s,
                 stitched_from_s, stitched_to_s } ]

  and add stitched_offset_s alongside each marker's existing
  offset_s. Your option B. offset_s keeps its current meaning
  and nothing that reads it today changes.

  transcribe_walk.py already decodes each part with PyAV and
  knows its true duration; having it write those durations into
  the transcript header makes stitched_from_s exact rather than
  chunk-count arithmetic.

  Touches:  recording.ts (one array write), schema.ts (one
            optional field), sessions.ts sidecarFor, export.ts,
            transcribe_walk.py (one header line).
  Risk:     LOW but not zero - it touches a file in the capture
            chain. Everything added is optional and additive;
            walks recorded before it read exactly as they do now.
  Fallback: if you would rather not touch recording.ts at all,
            say so. Part boundaries can be derived from
            segment_starts alone, accurate to about +/-3s, with

 7. SHARED WATER - WHAT IT ACTUALLY DOES TODAY
===============================================================

  Less than you think, and nothing contradictory.

  shared_water is a property of the PLANTER, in the registry. It
  affects exactly two things:

    1. Log care shows a planter chip that selects both plants at
       once, styled as shared, with the tooltip "Shared soil -
       one soak serves all of them".
    2. Plant Detail shows a "shared soil" tag instead of
       "separate pots".

  It affects NOTHING ELSE. Due dates, adherence, next_due,
  history and the calendars are all strictly per plant, on each
  plant's own interval. One soak writes two Water events, one
  per member, only because you selected both.

  So today: 015-PTH is judged on 10 days and 016-SYN on 7 days,
  from the same soak. Water on PTH's rhythm and SYN reads late;
  on SYN's rhythm and PTH reads early. Neither is wrong about
  the soil - the two numbers simply disagree about the same body
  of water.

  Nothing in the code is inconsistent. The DATA is: two
  different intervals describing one pot.

  THREE OPTIONS, smallest first:

    A. Change nothing in code. Set both members to the same
       interval, because it is one pot. Cost: you lose the
       record that these two species want different things.
       Effort: zero, and it is honest.

    B. Planter-level interval. shared_water planters get one
       interval and members inherit it. Each plant keeps its own
       reference intervals as SPECIES knowledge - what it would
       want alone - and the planter's is what adherence is
       judged against. Cost: a registry field, and derive.ts
       choosing which interval to use. This is the one I would
       pick.

    C. Judge the planter, not the plants. Adherence moves to the
       planter for shared members. Cost: real. Adherence is
       per-plant in the types, the screens and the history.

  I would not do C. The difference between B and C only shows up
  if you ever water one member and not the other, which you
  cannot do - they share soil.

  RECOMMENDATION: B, but it can wait. A is free today and costs
  you only a note. Nothing here is a defect.

 10. WHERE I DISAGREE
===============================================================

  a) "Have transcribe_walk.py produce structured metadata and
     let the app read verification state from it." I disagree.
     That makes the app TRUST the transcriber's verdict. The app
     has its own coverage gate and its own duration; letting it
     check the timestamps itself is both less code and more
     honest. Teach it the format, do not import the conclusion.
     (Same reasoning that had the WATCHER read the coverage line
     rather than recompute it - there, the transcriber is the
     authority; here, the app is.)

  b) Silent de-duplication of same-day Water. I disagree with
     the "silently skip" half. Refuse the selection, visibly,
     rather than dropping an event the log was asked to hold.
     Same outcome, no invisible behaviour. See 3d.

  c) "Export only screen-log entries relevant to review
     sessions." Already true - export.ts filters to entries
     belonging to the walks in the package. Nothing to do.

  d) Defaulting the review table to all-selected. Not proposed
     by you, but it is the obvious next step and I would resist
     it. One tap to select all; zero taps should not.

  e) Section 3's framing that the offset reset is inherent to
     the design. It was a bug and it is fixed. I would rather
     you knew that than accepted a limitation that no longer
     exists - but see the 357-vs-785 problem, which is real and
     is the actual reason to build the part map.
